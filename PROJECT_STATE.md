# Project Overview

The Live Trading Control Tower is an **institutional trading-operations platform** — a supervisory "mission control" for autonomously executing algorithmic FX strategies discovered by a separate research system (FX-OB-Research-Lab). It is not a charting app, not MetaTrader, not a broker terminal. Its centre of gravity is **Policy · Execution · Safety · Decision-making**: the operator observes, understands, decides, protects, executes, and audits. Charts exist only for inspection. The frontend is a production-quality, fully data-bound operator UI over a data seam; today it runs against a fixture backend, and the seam is designed so a live backend can replace the fixture with zero component changes.

**Principles that must never change:**
1. Server-authoritative — components render snapshots and emit intents; they never compute trading truth.
2. Presentational components — props in, typed callbacks out; no data fetching or business logic in leaves.
3. Contracts-first — never invent a field; missing → `// FLAG: CONTRACT REQUIRED` and stop.
4. One source of truth per concern — one formatter module, one colour/label mapper, one command vocabulary, one token file.
5. Single-implementation components — Badge, DataTable, Inspector (InspectorHost + renderers), ConfirmDialog, ActionBar, ChartPanel, DecisionChainView. Variants, never duplicates.
6. Explainability everywhere — every decision-bearing object answers "Why?" via the Decision Chain.
7. Frozen contracts, pair-first navigation (`/pair/:pairId/...`), token-only styling, the typed command layer (`Command` union → `useCommand` → ConfirmDialog), the data seam (`useRepository` selectors over shared query keys), and Strategy Package / Deployment Manifest semantics (Manifest wraps the immutable Package; every trade pins `packageHash`).

# Runtime Architecture

**Principle:** the **Fixture World is immutable** (authoritative bootstrap dataset, never mutated); **Runtime State is a mutable overlay** stored separately and layered over it. Reads = fixture ⊕ overlay.

**Backend (`backend/server.py`):**
- Store: SQLite `runtime.db` (parallel to `events.db`; lazy, gitignored) with one table `runtime_overlay(kind, entity_id, overlay JSON, updated_at)`, PK `(kind, entity_id)`. Kinds: `deployment`, `trade`, and `meta` (singleton `active_package` record). Orders overlay the `trade` kind (an order is a pending trade, resolved by `brokerOrderId`|`tradeId`).
- Read merge: `_deployments_view()` / `_live_trades_view()` map each fixture entity through `_apply_deployment_overlay` / `_apply_trade_overlay`, which shallow-merge visible overlay fields (and, for trades, append `_managementAppend` entries onto `management`). Internal `_`-prefixed keys (e.g. `_prevStatus`, `_managementAppend`) are stripped from the response.
- Write: `_apply_command_effects(name, payload, now)` maps each command to an overlay mutation and returns `(before, after)` used for the audit event. Deployment effects: Pause→`Paused` (remembers `_prevStatus`), Resume→restore prev, Kill/Flatten→`Locked` (+`lastAction`; Flatten also closes the deployment's open trades), SetLaneMode→`executionMode`, PausePair→all pair deployments `Paused`, GlobalKill→all `Locked`+`liveEnabled:false`. Trade effects: SLToBE→`sl=entry`, Move{SL,TP}→price when supplied (else audit-only, no price UI yet), Partial/ReduceRisk→`size/2`, Close→`state=closed`+closePrice/realizedR, AutoManagement→flag; all append a `management` entry.
- Idempotency: a replayed `Idempotency-Key` short-circuits in the command handler **before** effects run, so retries never double-apply.
- `POST /api/runtime/reset` clears overlays (audit log is never cleared).

**Frontend (replay only):** replay runtime is **view state, not trading truth**, so it lives in the shell store (`replay` slice) + `localStorage` (`ct.replay`), not the backend — backend-persisting a 2.5 Hz cursor would be wrong. `ensureReplayPair` realigns/clamps the cursor to the pair's window on mount (a `?t=` deep-link wins); `playing` never auto-resumes on load. This also retired the old "cursor resets on tab change" compromise.

**As of Step 4** the overlay also owns: order lifecycle (cancel/reduce/convert-to-ghost on the trade record), active-package selection (`meta/active_package`: current/previous/activatedAt/source; Deploy + Rollback; `/packages/active` + event `packageHash` follow it), deployment runtime metadata (`statusChangedAt`/`lastCommandAt`/`notes`), and Lock/Unlock. Runtime health is exposed via `GET /runtime/health` (computed, not stored). **Still NOT owned** (deferred): operator preferences. Deployment `riskState` aggregates (openTrades count, floatingPl) are still **not** recomputed when a trade closes — status/lifecycle only.

## Known Risks

- **Lazy-loading regressions** — a new lazy route can silently duplicate a store/QueryClient or leak charts/intervals. Mitigation: re-run the audit table above on every routing/store/chart/timer change.
- **Future WebSocket layer** — double subscriptions, cache races, leaks. Mitigation: one shell-level connection, patch Query cache by monotonic `seq`, re-snapshot on gap.
- **State/query duplication** — UI state → Zustand (2 stores by design), server state → Query, never both; every read through a shared `QK` key.
- **Persistence migration** — when world reads become DB-backed, response shapes must stay identical; migrate one endpoint at a time.
- **Event-store growth** — the append-only log grows unbounded; fine locally, needs retention/compaction thinking before production.
- **Large tables** — virtualize before row counts grow.
- **Fixture drift** — three-copy sync rule; drift silently breaks reads/tests.
- **Contract drift** — tightening a type or adding a field must be verified against `_fixtures/contracts.md`; flag, never invent.
- **Design drift** — any literal colour/px or second Badge/Table/Inspector is drift; review for it.
- **KNOWN_COMMANDS mirror** — the backend command set mirrors `lib/commands.ts` by hand; adding a command requires updating both (documented at both sites).
